Part I

The Audio World

Chapter 1Dante and Digital Audio Networking

Before ETR-NodeScope can monitor anything, audio has to be flowing. That audio lives on a Dante network — a standard that turns ordinary Ethernet switches into a professional audio router capable of carrying hundreds of channels with submillisecond latency.

What Is Dante?

Dante (Digital Audio Network Through Ethernet) was developed by Audinate, a company founded in Sydney, Australia in 2003. It carries uncompressed PCM audio as RTP/UDP packets over standard Ethernet. Every Dante-enabled device — wireless receiver, digital console, amplifier, stage box — appears as both a source and destination on the network, addressable by name.

🎓 Concept

The maths of audio over Ethernet

48,000 samples/sec × 24 bits × 64 channels = 73,728,000 bits/sec ≈ 74 Mbps Gigabit Ethernet capacity: 1,000 Mbps That's 13× headroom — one GbE port carries the full 64-channel load easily.

How ETR-NodeScope Receives Dante Audio

ETR-NodeScope does not handle Dante UDP packets directly. It uses Dante Virtual Soundcard (DVS) — a driver that presents the Dante network as an ASIO audio device to Windows. DVS handles all the protocol work; ETR-NodeScope reads the delivered audio the same way a DAW reads from an audio interface.

LayerWhat it does
Dante network (UDP/IP)Audio flows as RTP/UDP packets between devices on the LAN
Dante Virtual SoundcardReceives UDP packets, presents them as an ASIO device to Windows
ETR-NodeScope (ASIO client)Reads audio frames via the ASIO API — same as a DAW reading a sound card

From Float to dBu — How the Meter Works

ASIO delivers audio as 32-bit floats normalised to −1.0 to +1.0. ETR-NodeScope converts to dBu (a real-world voltage reference) using the EBU R68 calibration constant:

// ASIO delivers float samples where +1.0 = 0 dBFS // Professional standard: 0 dBFS ≈ +18 dBu (EBU R68) double dBFS = 20.0 * Math.Log10(Math.Abs(sample) + 1e-9); double dBu = dBFS + 18.0; // Example: sample = 0.5 → dBFS = -6.02 → dBu = +11.98

Question 1 of 5

What protocol does Dante use to carry audio across the network?

✓ Correct! Dante uses RTP (Real-time Transport Protocol) over UDP. UDP is chosen over TCP because it has lower overhead — there's no retransmission of lost packets, which would cause audio glitches.
✗ Incorrect. Dante uses RTP/UDP — real-time audio cannot afford TCP's retransmission overhead.
Question 2 of 5

Why does ETR-NodeScope use Dante Virtual Soundcard rather than connecting to the Dante network directly?

✓ Correct! DVS abstracts all the complexity — RTP packetising, IEEE 1588 PTP clock sync, subscription management. ETR-NodeScope just reads audio frames via ASIO.
✗ Not quite. The key reason is abstraction — DVS handles the entire Dante protocol stack so ETR-NodeScope only needs to implement a standard ASIO client.
Question 3 of 5

What is ASIO and why does it matter for ETR-NodeScope?

✓ Correct! ASIO was created by Steinberg in 1997 to solve the latency problem in Windows audio. Its callback model is essential — the driver calls your function at precise 10.7ms intervals, and if you miss the deadline, you get a dropout.
✗ ASIO stands for Audio Stream Input/Output, created by Steinberg in 1997. It reduces Windows audio latency from ~200ms to 3–10ms by bypassing the audio mixer.
Question 4 of 5

At 48,000 Hz with a 512-sample ASIO buffer, how often does ETR-NodeScope's audio callback fire?

✓ Correct! 512 samples ÷ 48,000 samples/sec = 0.01067 seconds = 10.67ms. The callback must return before the next one fires or you get a dropout.
✗ The calculation is 512 ÷ 48,000 = 0.01067 seconds = 10.7 milliseconds.
Question 5 of 5

What does the +18 dBu offset in the ETR-NodeScope level calculation represent?

✓ Correct! The EBU R68 standard defines 0 dBFS ≈ +18 dBu. Without this offset, digital levels (dBFS) would be meaningless to an engineer who thinks in terms of real-world voltages.
✗ The +18 dBu offset is the EBU R68 calibration constant — it converts digital dBFS into the real-world dBu values that audio engineers are familiar with.
Part II

History of the Protocols

Chapter 2A History of Every Protocol ETR-NodeScope Uses

Every technology in ETR-NodeScope has a story. Understanding where these standards came from — who invented them, what problem they solved, what constraints they were designed under — makes them much easier to understand and remember.

1937
PCM — Pulse Code Modulation (Alec Reeves, ITT Paris) Reeves filed French patent 852,183 on 22 October 1937 — the idea of sampling an audio waveform at regular intervals and storing each measurement as a binary number. He could not get anyone interested; the patent expired in 1954 before it was exploited. The idea only became practical when Bell Labs used it for military voice encryption (SIGSALY, 1943). PCM reached consumer audio in 1980 with the Compact Disc. Every piece of digital audio in ETR-NodeScope is PCM.
1960
RS-232 — Serial Communication Standard (EIA) The Electronic Industries Association published RS-232 in 1960 to define how computers communicate with modems. By the 1980s it became the universal AV control language — every rack-mount device had an RS-232 port accepting text commands like POWER ON\r. When Ethernet replaced RS-232 in the 2000s, manufacturers simply wrapped the same ASCII commands in TCP sockets. Wireless's port 2202 protocol — < GET 1 BATT_CHARGE > — is RS-232-era design philosophy running over modern TCP/IP.
1974
TCP/IP — Cerf and Kahn, IEEE Transactions on Communications Vint Cerf and Bob Kahn published "A Protocol for Packet Network Intercommunication" in 1974, defining the two-layer model: IP handles routing and addressing; TCP adds guaranteed delivery, in-order reassembly, and flow control. Everything ETR-NodeScope does over the network runs on TCP/IP. The three-way handshake (SYN, SYN-ACK, ACK) plus ARP resolution on link-local addresses is why ETR-NodeScope uses an 800ms TCP probe timeout for Wireless discovery.
1983
MIDI — Musical Instrument Digital Interface Published August 1983 by a consortium including Roland, Yamaha, Korg, and Sequential Circuits. MIDI's 31.25 kBaud serial connection and 7-bit value resolution (0–127) were appropriate for 1983 microcontrollers. By the 1990s its limitations — no floating-point values, no network transport, fixed message types — were painful. MIDI's shortcomings directly motivated the design of OSC.
1991
WAV File Format — Microsoft and IBM WAV was introduced as part of Windows 3.1 multimedia extensions, built on the RIFF (Resource Interchange File Format) container developed with IBM, itself derived from Electronic Arts' IFF format (1985). The format uses a 44-byte header describing the audio, followed by raw PCM samples. ETR-NodeScope writes this header before streaming audio over HTTP so media players (VLC, browser <audio> tags) can decode the stream. The format is 34 years old and every media player still reads it.
1997
ASIO — Audio Stream Input/Output (Steinberg) Steinberg created ASIO to solve Windows audio latency. Windows' 1990s audio stack was designed for game sound effects (100–200ms latency acceptable). Professional recording demands real-time monitoring at under 10ms. ASIO bypasses the Windows audio mixer and talks directly to hardware drivers, enabling 3–10ms latency. Its callback model — the driver calls your function at precise intervals — is fundamental to ETR-NodeScope's audio pipeline.
1997
OSC — Open Sound Control (Wright & Freed, CNMAT, UC Berkeley) Presented at the International Computer Music Conference in 1997. Designed as everything MIDI was not: 32-bit float values instead of 7-bit integers, arbitrary URL-like address patterns (/etr-nodescope/channel/1/battery) instead of fixed message types, UDP over any network instead of a serial wire, and 64-bit NTP timestamps for precise scheduling. ETR-NodeScope sends OSC for Qlab integration, lighting console triggers, and custom monitoring scripts.
1999
MQTT — Message Queuing Telemetry Transport (Stanford-Clark & Nipper, IBM) Invented by Andy Stanford-Clark of IBM and Arlen Nipper of Arcom to monitor oil pipelines across the Sahara desert over expensive, unreliable satellite links. Design goals: minimal bandwidth (every byte matters at USD 10/KB), reliable delivery (QoS levels), low power, publish/subscribe broker model. IBM kept it proprietary until 2013 when it was released to OASIS, coinciding with the IoT boom. ETR-NodeScope uses MQTTnet (a .NET library) to publish channel state with QoS 1 (at-least-once delivery).
2000
REST — Roy Fielding's PhD Thesis, UC Irvine Roy Fielding (co-author of HTTP/1.1) defined REST (Representational State Transfer) in his 2000 PhD thesis. REST constraints — stateless requests, uniform interface (GET/PUT/POST), self-describing messages — made web services scalable and interoperable. Wireless's SSC v2 API (used by ETR-NodeScope for digital wireless receiver receivers) is a REST API. The contrast with Wireless's ASCII protocol illustrates 20 years of API design evolution.
2001
JSON — JavaScript Object Notation (Douglas Crockford) Crockford formalised JSON around 2001, published RFC 4627 in 2006. JSON is a subset of JavaScript object literal syntax that had existed since 1995 — Crockford's contribution was identifying it as a useful standalone data format. Wireless's protocol uses JSON push messages; ETR-NodeScope's WebSocket messages to browsers are JSON; MQTT payloads are JSON. The contrast with Wireless's ASCII strings shows how data serialisation has evolved.
2002
mDNS / Bonjour (Stuart Cheshire, Apple) Apple shipped Rendezvous (later renamed Bonjour) in Mac OS X 10.2 as part of the zero-configuration networking initiative. mDNS sends DNS queries to multicast address 224.0.0.251:5353 — any device that matches responds directly, no DNS server needed. Standardised as RFC 6762 in 2013. ETR-NodeScope uses mDNS to find Wireless digital wireless receiver receivers and — critically — to find the control interface IP of digital wireless receivers (AD4D-A, AD4Q) which is different from the Dante audio interface IP.
2003
Dante — Audinate (Sydney, Australia) Audinate was founded in 2003 as a spin-out from the University of Technology Sydney. Dante went commercial around 2006. Yamaha was the first major manufacturer to adopt it (2009 digital consoles). The predecessor, CobraNet (Cirrus Logic, 1996), required special hardware and managed switches. Dante runs on commodity GbE with no special infrastructure. Today Dante is the dominant professional audio networking standard with thousands of compatible products.
2006
Server-Sent Events (Ian Hickson, Opera) Hickson developed SSE at Opera Software and included it in the WHATWG HTML Living Standard. SSE holds an HTTP connection open and streams text events as they occur — simpler than WebSocket for one-directional push use cases. Standardised as RFC 8895. Wireless chose SSE for SSC v2 because digital wireless receiver is a monitoring tool: data flows from receiver to controller. Commands (mute, gain) are separate HTTP requests, not sent back over the SSE stream.
2011
WebSocket (RFC 6455) WebSocket was developed as part of HTML5, published as RFC 6455 in December 2011. It upgrades an HTTP connection to a full-duplex TCP stream via the Upgrade header. Before WebSocket, real-time web apps used polling (GET every second), long-polling (hold response open), or HTTP streaming (Comet) — all awkward. ETR-NodeScope's WebUI uses WebSocket for JSON state updates (text frames) and PCM audio (binary frames) on the same connection simultaneously.

Chapter 2 Quiz

History of the Protocols — 5 questions, pass mark 60%

Question 1 of 5

PCM was invented in 1937 by Alec Reeves. Why was it not commercially exploited until the 1970s?

✓ Correct! Reeves' patent expired in 1954, unrealised, because the vacuum tubes needed to process PCM fast enough were too expensive and bulky. Integrated circuits in the 1970s finally made it practical for consumer audio.
✗ The main barrier was hardware — practical PCM processing required electronic switching speeds that couldn't be achieved cheaply until integrated circuits in the 1970s. The patent expired in 1954 without being commercially exploited.
Question 2 of 5

Why does Wireless's TCP/2202 protocol look like RS-232 serial commands with angle brackets and spaces?

✓ Correct! Legacy protocols on new transports is extremely common in AV. When networks replaced serial cables, manufacturers took the path of least resistance — same commands, new transport. This is why ETR-NodeScope's entire Wireless parser is a regex and a string split.
✗ The ASCII format is 1990s RS-232 design. When Ethernet replaced serial cables, Wireless simply wrapped the existing commands in TCP rather than redesigning from scratch.
Question 3 of 5

MQTT was invented to solve a problem in which industry, and what were the three key design constraints?

✓ Correct! Stanford-Clark and Nipper at IBM designed MQTT in 1999 for oil pipelines across the Sahara. Satellite data cost USD 10/KB, sensors ran on solar power, and the link dropped regularly. These constraints produced a remarkably efficient protocol that became the standard for IoT 15 years later.
✗ MQTT was invented for oil pipeline monitoring across the Sahara desert. The constraints were minimal bandwidth (satellite data was USD 10/KB), reliable delivery, and low power consumption.
Question 4 of 5

Why did Wireless choose Server-Sent Events (SSE) for digital wireless receiver receivers rather than WebSocket or raw TCP?

✓ Correct! SSE is one-directional by design — perfect for monitoring where the receiver pushes state changes and the controller sends occasional commands via separate HTTP PUT requests. SSE also works through HTTP proxies that might block WebSocket upgrades.
✗ The key is that digital wireless receiver is a monitoring system — data flows one way (receiver to controller). SSE is designed for exactly this pattern, works through HTTP proxies, and has automatic reconnection built in.
Question 5 of 5

What was the fundamental problem that led to the creation of WebSocket in 2011?

✓ Correct! Before WebSocket, developers used polling (GET every second), long-polling (held response), or Comet (HTTP streaming with a permanently loading page). All were hacks. WebSocket solved the fundamental problem: HTTP was never designed for server-initiated messages.
✗ The core problem was that HTTP is request-response — browsers could only receive data by asking for it repeatedly. WebSocket enables true bidirectional communication where the server can push messages the moment something happens.

Chapter 3How ETR-NodeScope Is Structured

ETR-NodeScope is a C# / .NET 8 desktop application using Avalonia UI. Its architecture separates concerns into layers — each layer has one job, communicates upward via events, and knows nothing about the layers above it.

LayerClassesResponsibility
ModelsWirelessChannelState, ChannelStateDto, AlertModelPure data — no logic, no UI
ServicesShureDeviceClient, DiscoveryService, SmartAlertsEngine, WebUIServerAll business logic and hardware communication
ViewModelsMainViewModel, ChannelTileViewModelTranslate service data into bindable UI properties
ViewsMainWindow.axaml, ChannelTile.axamlXAML layout — no logic, binds to ViewModel properties
IntegrationMqttService, OscService, SessionLogServiceMQTT broker, OSC UDP, log files

The 12-Step Journey from Transmitter to Tile

1. Transmitter embeds battery % in RF side-channel (~400 bits/sec) 2. Receiver demodulates: "< REP 1 BATT_CHARGE 078 >" 3. BaseDeviceClientAdapter.ReceiveLoopAsync() reads the line 4. ShureDeviceClient.ParseMessage() routes → HandleRep() 5. case "BATT_CHARGE": state.BatteryPercent = 78 6. PublishChannelIfChanged() compares with last published snapshot 7. If changed → RaiseChannelDataReceived(channel=1, state) 8. C# event fires → all subscribers notified simultaneously 9. MainViewModel.OnDeviceChannelData() receives it 10. tile.BatteryDisplay = "78%" 11. tile.BatteryLevel = 0.78 12. Avalonia data binding updates the tile — no explicit UI code
🎓 Concept

The Observer Pattern — C# events

Step 7–9 uses C# events — a built-in implementation of the Observer pattern (Gang of Four, 1994). ShureDeviceClient fires an event; MainViewModel, SmartAlertsEngine, WebUIServer, and SessionLogService all subscribe. ShureDeviceClient knows nothing about any of them:

// ShureDeviceClient declares the event: event Action<int, WirelessChannelState>? ChannelDataReceived; // Fires it after parsing a REP message: RaiseChannelDataReceived(channel, state); // All four subscribers run — ShureDeviceClient knows nothing about them: mainViewModel.ChannelDataReceived += OnDeviceChannelData; smartAlertsEngine.ChannelDataReceived += EvaluateChannel; webUIServer.ChannelDataReceived += PushStateToClients; sessionLogger.ChannelDataReceived += MaybeLogBatterySwap;

Change Detection — Not Every Frame Reaches the UI

Wireless sends SAMPLE frames every 100ms. ETR-NodeScope filters them before the UI is updated — only meaningful changes cause a redraw:

private void PublishChannelIfChanged(int channel, WirelessChannelState state) { var snapshot = ChannelPublishSnapshot.From(state); if (_lastPublishedState.TryGetValue(channel, out var previous) && !snapshot.HasMeaningfulChangeFrom(previous)) return; // RF changed by 0.5 dBm? Skip the UI update. _lastPublishedState[channel] = snapshot; RaiseChannelDataReceived(channel, state); // Something real changed }

WebUI Audio Path — Float to Browser

// Called every 10.7ms from ASIO callback // Converts ASIO float32 → PCM int16 → WebSocket binary frames unsafe { fixed (float* pIn = frame) fixed (byte* pOut = pcm) { short* pS = (short*)pOut; for (int s = 0; s < totalSamples; s++) { float v = Math.Clamp(pIn[s * channelCount + ch], -1f, 1f); pS[s] = (short)(v * 32767f); // float → int16 } } } // 128 samples × 2 bytes = 256 bytes per WebSocket binary frame // 375 frames/sec, each 2.67ms apart

Software Architecture — 5 questions, pass mark 60%

Question 1 of 5

What is the purpose of PublishChannelIfChanged() in ETR-NodeScope?

✓ Correct! Without this filter, 10 SAMPLE frames per second per channel would all trigger UI redraws. The snapshot comparison means only actual changes (battery dropping 1%, RF dropping 3 dBm) cause a redraw.
✗ PublishChannelIfChanged() is a change detection filter. It compares new state with a stored snapshot and only fires the update event when something meaningful changed.
Question 2 of 5

In MVVM, what is the ViewModel's role and why is it important?

✓ Correct! The ViewModel is the translator. ShureDeviceClient produces WirelessChannelState with a BatteryPercent integer. ChannelTileViewModel formats that as "78%" for the TextBlock binding. The service doesn't know about UI; the View doesn't know about services.
✗ The ViewModel bridges services and UI. It receives raw service data, formats it into display strings and normalised values, and exposes them as properties. The key benefit is decoupling — services don't import UI classes and vice versa.
Question 3 of 5

Why does ETR-NodeScope start the receive loop before calling ConnectDeviceAsync()?

✓ Correct! A race condition: if ConnectDeviceAsync runs first and sends GET 0 MODEL, the receiver might send the REP before the receive loop is listening. Starting the loop first eliminates this race.
✗ It's a deliberate choice to prevent a race condition. If connection happened before the loop started, the receiver might send the MODEL or NUM_CH response before anything is listening for it.
Question 4 of 5

When ETR-NodeScope converts ASIO float audio to PCM-16LE for WebSocket streaming, why multiply by 32767 rather than 32768?

✓ Correct! Signed 16-bit integers (short in C#) range from -32768 to +32767. The positive maximum is 32767. Multiplying +1.0f × 32768 = 32768, which doesn't fit in a short and wraps to -32768 — a loud click. Hence 32767.
✗ Signed 16-bit integers range from -32768 to +32767. The maximum positive value is 32767. Multiplying by 32768 for a +1.0 input would produce 32768, which overflows to -32768 in a short — an audible click.
Question 5 of 5

What is the Observer pattern and how does ETR-NodeScope use it?

✓ Correct! The Gang of Four defined the Observer pattern in 1994. C# events are a language-level implementation. The key benefit is decoupling — ShureDeviceClient has zero imports from MainViewModel, SmartAlertsEngine, WebUIServer, or SessionLogService.
✗ The Observer pattern (Gang of Four, 1994) defines a Subject-Observer relationship where the Subject notifies its Observers when state changes, without knowing who they are. C# events are a built-in implementation.

Part IV Quiz

Wireless Protocols — 5 questions, pass mark 60%

Question 1 of 5

A Wireless AD4D-A sends < REP 1 RX_RF_LVL 043 >. What is the actual RF level in dBm, and which device family is this?

✓ Correct! The key insight: RX_RF_LVL is a wireless receiver parameter (offset −128). digital wireless uses RSSI (offset −120). The AD4D-A is digital wireless — so in practice it would send RSSI, not RX_RF_LVL. If it were wireless receiver: 43 − 128 = −85 dBm. This is a weak signal — 1 bar.
✗ wireless receiver uses RX_RF_LVL with offset −128. digital wireless uses RSSI with offset −120. For wireless receiver: 43 − 128 = −85 dBm (weak signal). For digital wireless: 43 − 120 = −77 dBm (acceptable).
Question 2 of 5

ETR-NodeScope receives: < SAMPLE 1 RSSI A 083 > from an digital wireless receiver. What does it do with this message?

✓ Correct! The keyword SAMPLE detection is elegant: if parts[2] is not a number, it's a keyword frame. Synthesise a REP array and reuse the existing HandleRep parser — no duplicate code needed.
✗ ETR-NodeScope detects keyword SAMPLE frames by checking if parts[2] is numeric. If not, it synthesises a REP frame array and routes it through HandleRep() — reusing the existing parser.
Question 3 of 5

What does Wireless's SSE subscription PUT request do and why is it necessary?

✓ Correct! SSC v2 is designed for efficiency — the controller specifies exactly what it wants. ETR-NodeScope subscribes to 10 paths per channel. The receiver only streams changes to those paths, not its entire internal state.
✗ The PUT subscription tells the receiver which specific resource paths to include in the event stream. ETR-NodeScope subscribes to 10 paths per channel (battery, RF level, audio level, mute, gain, etc.).
Question 4 of 5

Why does Wireless's ChannelDataReceived call use chIndex - 1 when invoking the event?

✓ Correct! This is a classic off-by-one conversion. Wireless counts channels from 1. ETR-NodeScope's tile indices start at 0. Without the -1, every Wireless channel would appear on the wrong tile.
✗ It's a 1-based to 0-based conversion. Wireless numbers channels starting from 1 (CH1, CH2). ETR-NodeScope tiles are 0-indexed. Subtracting 1 aligns them correctly.
Question 5 of 5

ETR-NodeScope discovers a Wireless receiver at 169.254.158.222 via multicast and at 169.254.100.134 via TCP fingerprint. It connects to 169.254.100.134. Why?

✓ Correct! The AD4D-A dual-interface problem is one of the most important practical details in ETR-NodeScope. The Dante audio port responds to some port 2202 commands but doesn't give full data. ETR-NodeScope's source-tagging system solves this automatically.
✗ The AD4D-A has two network interfaces — the Dante audio port (found via multicast) and the control port (found via mDNS + TCP fingerprint). ETR-NodeScope tags the multicast-only IP and skips it when a verified control IP exists.

Part V Quiz

Using the Software — 5 questions, pass mark 60%

Question 1 of 5

ETR-NodeScope's tiles are showing "---" for channel name, battery, and frequency after connecting. What is the most likely cause?

✓ Correct! This is the most common Wireless digital wireless connection problem. The Dante audio port gives partial data — RF bars may even work. But channel name, battery, and frequency come only from the control port.
✗ When tiles show --- for name/battery/frequency but RF might still work, the likely cause is connecting to the Dante audio port instead of the control port. Enable mDNS discovery or add the control IP manually.
Question 2 of 5

A Wireless receiver is not appearing in ETR-NodeScope's Connected Devices panel. You have verified the IP is reachable. What should you check first?

✓ Correct! And remember: Wireless doesn't use multicast. You must always add Wireless IPs manually — they will never be auto-discovered. Then check no other tool (Wireless Manager) holds port 32789.
✗ The first check for Wireless is the single-controller restriction. Also remember: Wireless has no multicast, so you must add the IP manually in Settings → Wireless Devices regardless.
Question 3 of 5

What is the purpose of the Release Readiness check in ETR-NodeScope?

✓ Correct! Run Release Readiness before every show. All checks should show green. A red check (e.g. port 8427 already bound) indicates a configuration problem that could prevent normal operation.
✗ Release Readiness is a pre-show automated checklist. It tests 12+ conditions that need to be right for ETR-NodeScope to function properly — socket bindings, licence validity, ASIO availability, and more.
Question 4 of 5

You want a tablet operator to view the WebUI and be able to send mute commands, protected by a password. What settings do you need?

✓ Correct! Three settings needed: Allow Remote Clients (enables access from other devices), Enable Remote Commands (allows control, not just monitoring), and Shared Secret (token-based authentication). The token goes in the URL on first visit, then is stored locally in the browser.
✗ You need: Allow Remote Clients ON (opens access to other devices), Enable Remote Commands ON (allows mute/control — not just monitoring), and a Shared Secret. The token goes in the URL: http://[ip]:8080/?token=yourpassword.
Question 5 of 5

Why does the WebUI audio stream work in Chrome but a student reports no audio in their browser despite the connection indicator being green?

✓ Correct! Browser autoplay policy has been strict since 2018. The Web Audio API requires a user gesture (click, tap, or keypress) before audio context can be created and audio played. This applies to all browsers — Chrome, Safari, Firefox, Edge.
✗ This is the browser autoplay policy in action. All modern browsers require a user gesture before playing audio. The student needs to click anywhere on the page first, then double-click the tile to start monitoring.
